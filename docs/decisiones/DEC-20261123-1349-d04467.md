## Contexto

La base tiene 4 roles (`organizadora`, `cocinera`, `nutricionista`, `admin`) **por olla**. El admin no
es global: el de una olla ve 0 de otra. El nutricionista puede leer salud y el agregado, pero **no
puede firmar, publicar ni aprobar**: no hay policy de escritura y `UPDATE menu_template` devuelve 0
filas. La cocinera ve salud por `evento_sync`. No hay auditoría de firmas.

## Decisión

Separar **admin de plataforma** (global) de los roles **por olla**. El nutricionista ejecuta acciones
cortas —firmar, publicar, retirar, aprobar o rechazar con motivo— con **auditoría append-only**. La
cocinera no lee salud individual. La organizadora da de alta, corrige y da de baja el padrón. Cada
acción se autoriza por rol y por olla, no por “estar autenticado”.

## Alternativas descartadas

| Alternativa | Por qué no |
|---|---|
| Un solo admin por olla | no puede crear ollas ni asignar roles |
| Nutricionista sin escritura | el menú firmado queda congelado en el seed |
| Auditoría en logs de aplicación | no es evidencia, se pierde |
| Permisos por UI | la API se llama directo con el JWT |

## Consecuencias

- Migración con `app.es_admin_global()`, policies de UPDATE/INSERT para menú, validación y
  sustituciones, y `revoke` de salud en el pull.
- Tabla `auditoria` (append-only) con actor, olla, entidad, acción, motivo y hash.
- La UI muestra u oculta acciones según rol; el servidor vuelve a decidir.
- Tests de matriz 4 roles × 6 tablas y 42501 para lo prohibido.

## Cómo se verifica que se cumple

pgTAP: admin global ve 2 ollas; administrador de olla 2 no ve olla 1; nutricionista firma y queda una
fila de auditoría; cocinera recibe 42501 al intentar firmar o leer salud. Sin esos tests, no se cierra.
