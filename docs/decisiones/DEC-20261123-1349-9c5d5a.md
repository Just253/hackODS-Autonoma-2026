## Contexto

Hoy el backend corre en Supabase local (Docker/Podman) y la PWA es offline-first: la demo no depende
de la red. El siguiente paso es desplegar a Supabase Cloud y dar una URL real, con un administrador y
usuarios. Sin enrolamiento (#62), un JWT real ve 0 filas; sin write path (#65), lo que la app escribe
no llega a las tablas.

## Decisión

Mantener **Supabase local** para desarrollo y demo, y desplegar a **Supabase Cloud** cuando #62 y #65
estén cerrados. El admin y los usuarios se crean **por seed o por `enroll()`**, nunca con
`service_role` en el cliente ni con contraseñas compartidas. La URL y la publishable key se inyectan
por entorno; el modo offline sigue siendo el camino principal.

## Alternativas descartadas

| Alternativa | Por qué no |
|---|---|
| Seguir solo local | no se puede probar desde otra máquina ni con un tercero |
| Cloud ya, sin enrolamiento | todos los JWT ven 0 filas y la RLS parece rota |
| `service_role` en la PWA para “que funcione” | salta toda la RLS y filtra la clave |
| Usuarios a mano en el dashboard | no es reproducible ni testeable |

## Consecuencias

- `apps/web` lee `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY`; nada hardcodeado.
- Migraciones forward-only; `db push` a cloud solo después de `db:test` verde.
- Admin: un seed/script idempotente crea el member admin y su `device`; la contraseña se entrega una
  vez y se cambia al primer ingreso.
- Prohibido: `service_role`, Studio público, seeds con datos reales, contraseñas en el repo.
- La RLS se prueba contra cloud con un JWT anónimo (0 filas) y uno enrolado (1 olla).

## Cómo se verifica que se cumple

`pnpm db:test` en local; un smoke test contra cloud: anon → 0 filas, JWT enrolado → 1 olla, escritura
permitida solo a su rol. Si el smoke falla, no se publica la URL.
