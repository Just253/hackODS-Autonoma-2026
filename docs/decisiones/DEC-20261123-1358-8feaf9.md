## Contexto

La base ya distingue `organizadora`, `cocinera`, `nutricionista` y `admin` por olla, pero la UI no: hay
una sola perspectiva (PRB-20261123-1358-dbf227). El producto promete que cada rol ve lo suyo y que el
admin es global.

## Decisión

Toda pantalla vive dentro de una **sesión de contexto** `{memberId, ollaId, rol}`:

- **Divisor de contexto** visible: `Olla San Juan · Cocinera`, con selector de olla si el rol tiene
  varias y cambio de rol **solo en modo demo**.
- **Navegación por rol**: cocinera (servicio/menú), organizadora (padrón/dinero/precios/entre ollas),
  nutricionista (menú/salud agregada/firma), admin (ollas/miembros/catálogo/auditoría).
- **Guardas** de ruta y de acción; el servidor vuelve a decidir con `olla_members` y responde 42501.
- En cloud, la sesión sale del JWT; en demo, de un selector persistido. El CSS nunca es la única
  barrera.

## Alternativas descartadas

| Alternativa | Por qué no |
|---|---|
| Un solo shell con botones ocultos | la API queda abierta y la demo no muestra roles |
| Cuatro apps separadas | duplica navegación y estados |
| Selector de rol sin guardas | el jurado puede entrar a lo que no corresponde |

## Consecuencias

- `Shell`/`navegacion` reciben la sesión; cada ruta declara roles permitidos.
- Tests de navegación por rol y de 42501 para lo prohibido.
- El admin de plataforma es global; el resto, por olla (DEC-20261123-1349-d04467).
- La UI no muestra salud individual a la cocinera ni dinero si el rol no lo pide.

## Cómo se verifica que se cumple

Matriz de 4 roles × 7 rutas: cada uno ve solo lo suyo; llamar a una ruta prohibida devuelve 42501 o
redirige; el divisor muestra la olla y el rol correctos. Sin esos tests, no se cierra.
