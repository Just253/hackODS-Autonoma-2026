## Qué se observa

El backend no tiene la capa de operación que lo hace usable:

- `db:types` existe en `package.json`, pero **`packages/contracts/src/db.types.ts` no está** en el repo.
- No hay plan de backups ni prueba de restauración.
- No hay retención/borrado de fotos y audios (la captura promete borrado por confirmación).
- No hay observabilidad (métricas/errores) ni límites de tasa en las Edge Functions.
- El seed no crea `auth.users` ni `devices`, así que la RLS no se puede probar con un JWT real.

## Cómo se reproduce

```sh
rg --files packages/contracts/src | rg "db\.types"   # vacío
rg -n "backup|retención|retention|storage" supabase docs   # solo promesas
```

## Impacto

Los contratos se desalinean de la base sin que el compilador chiste; un borrado o un backup mal hecho
pierde datos de una olla; los adjuntos quedan para siempre. Con tres máquinas, la deriva es cuestión de
días.

## Qué se esperaba

Tipos generados y commiteados, backups con restauración probada, retención de adjuntos, métricas
básicas y límites de tasa; el enrolamiento (#62) para probar la RLS.

## Evidencia

- `package.json` (`db:types`) sin el archivo.
- Auditoría del backend 2026-11-23 (sin backups/observabilidad; `evento_sync` sin límites).
- PR #56 agrega `db.types.ts`, pero queda inerte hasta mergear y regenerar.

## Opciones y decisión

| Opción | Costo | Riesgo | Veredicto |
|---|---|---|---|
| Generar tipos a mano | bajo | se desactualiza | no |
| `db:types` en CI + commit del archivo | bajo | hay que regenerar en cada migración | **sí** |
| Backups solo del hosting | bajo | nadie probó la restauración | complementar |

## Cómo se cierra

`db.types.ts` commiteado y verificado en CI; un backup restaurado en un stack limpio; una política de
retención para fotos/audio con test; métricas mínimas de salud y errores. Sin eso, no se declara
“usable”.
