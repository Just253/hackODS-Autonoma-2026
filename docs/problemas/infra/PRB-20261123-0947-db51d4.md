## Qué se observa

GitHub tiene **41 labels**, varios de ellos duplican el set canónico de `docs/PROTOCOL.md` §3.7 y
`.github/labels.yml`. Un agente que filtra por `status:review` no ve los issues marcados
`status:in-review`, y no hay ningún error: simplemente no encuentra nada.

## Cómo se reproduce

```bash
gh label list --limit 60 --json name --jq '.[].name'
```

Salida real (2026-11-23), agrupada:

```text
canónicos válidos:  status:triage  status:ready  status:claimed  status:in-review  status:blocked
                    area:web  area:api  area:contracts  area:infra
                    type:bug  type:feat  type:chore  type:docs  type:spike
                    p0  p1  p2  needs:human  needs:decision

duplicados del canónico:  status:review  status:done  type:feature  good-first-issue
fuera del set:            accessibility  bug  documentation  duplicate  enhancement  help wanted
                          good first issue  invalid  question  wontfix
                          area:docs  area:nutricion
                          needs-verification  coordination  handoff
```

Uso real de los problemáticos (`gh issue list --label <l> --state all`):

| Label | Issues |
|---|---|
| `status:review` | 0 |
| `status:done` | 0 |
| `type:feature` | 0 |
| `good-first-issue` | 0 |
| `needs-verification` | 1 |

## Impacto

Tres personas y sus agentes van a mezclar `status:review` con `status:in-review` — el mismo error
que obligó a reescribir `docs/ORQUESTACION.md`. Cuesta tiempo de orquestación, no código.

## Qué se esperaba

Un solo label por concepto, el de `.github/labels.yml`.

## Evidencia

- Lista completa: salida de `gh label list` de arriba.
- `docs/FUENTES.md` §Pendientes ya anotaba `needs-verification` como fuera del set.
- La confusión `status:review`/`status:in-review` ya está documentada como error corregido en
  `docs/ORQUESTACION.md`.

## Opciones y decisión

| Opción | Costo | Riesgo | Veredicto |
|---|---|---|---|
| Borrar todos los que no están en `labels.yml` | 5 min | borrar un label lo quita de los issues que lo usan, sin aviso | **no** |
| Migrar el issue con `needs-verification`, después borrar los de 0 uso | 10 min | ninguno: los de 0 uso no pierden información | **sí** |
| Convivir con ambos sets | 0 | el error de filtrado sigue para siempre | no |

## Cómo se cierra

1. `gh issue list --label needs-verification --state all` → reetiquetar ese issue con el canonical
   que corresponda (`status:ready` o `needs:decision`), y comentar por qué.
2. Borrar sólo los de 0 uso: `gh label delete status:review`, `status:done`, `type:feature`,
   `good-first-issue`. Los de GitHub por defecto (`bug`, `question`, …) se dejan: no se usan pero
   tampoco confunden con `status:*` ni `type:*`.
3. Prueba de cierre: `gh label list --json name --jq '.[].name' | rg 'status:review|status:done|type:feature'`
   sin resultados, y `gh label list --limit 60 | wc -l` igual al número de filas de `.github/labels.yml`
   más los de GitHub.
